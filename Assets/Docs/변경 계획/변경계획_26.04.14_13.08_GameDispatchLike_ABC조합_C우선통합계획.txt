b. 요구한 기능
================================================================

  [ 결정 사항 ]
  - 조합 A, B, C 전부 진행한다
  - C 조합부터 시작해 B, A 순서로 단계적 확장

  ─────────────────────────────────────────────────────────────
  Q. ABC 전부 진행해도 되는가?
  ─────────────────────────────────────────────────────────────
  ✅ 된다. 이유:

  A+B+C의 합집합은 아래 9개 시스템이다.
  UI/View 시스템(⑨)만 빠진 상태로, 스크립트 레벨의 모든
  핵심 로직을 포함하는 구성이다.

  ┌────────────────────────────────────────────────────────────┐
  │ 시스템               │ 포함조합 │ 설치 순서 │ DOTween 필요 │
  ├────────────────────────────────────────────────────────────┤
  │ ③ 유틸리티           │ A, B, C  │ 1순위      │ 없음         │
  │ ② 오디오             │ B        │ 2순위      │ 없음         │
  │ ① 경로탐색 (BFS)     │ A, B     │ 2순위      │ 없음         │
  │ ⑤ 캐릭터 관리        │ A, C     │ 3순위      │ 없음         │
  │ ⑦ Day 진행           │ C        │ 4순위      │ 없음         │
  │ ⑧ 세이브/로드        │ C        │ 5순위      │ 없음         │
  │ ④ 길드               │ A        │ 6순위      │ 없음         │
  │ ⑥ 임무(파견)         │ A        │ 7순위      │ 없음         │
  └────────────────────────────────────────────────────────────┘

  ★ 중요 발견: 실제 코드를 확인한 결과,
    GameDispatchLike의 C# 스크립트들은 DOTween을 사용하지 않는다.
    DOTween은 UI/View 레이어에서만 사용될 가능성이 있으므로,
    A+B+C 범위에서는 DOTween 설치가 불필요하다.

  [ C 조합 포함 시스템 상세 ]

  ③ 유틸리티 (Utils)
    - Singleton<T>         : 모든 Manager의 기반 패턴
    - ClassExtentions.cs   : 확장 메서드 모음
    - PolygonIntersection  : 기하학적 충돌 계산
    - StringUtils          : 문자열 유틸

  ⑤ 캐릭터 관리 (Character)
    - CharacterUnit        : 캐릭터 상태/레벨/스탯/이벤트 관리
    - StatManager          : Strength, Endurance, Agility, Charisma, Intelligence
    - Team                 : 캐릭터 그룹핑 + 팀 스탯 집계
    - LevelProgression     : 레벨업 로직
    - CharacterSO          : ScriptableObject 캐릭터 설정값

  ⑦ Day 진행 (Day System)
    - DayManager           : 하루 사이클 제어 (시작/종료/일시정지)
    - DayCharacterManager  : 캐릭터 상태 머신 (Available→Mission→Resting)
    - DaySO                : ScriptableObject 하루 설정값
    - DayReport            : 일일 미션 결과 집계

  ⑧ 세이브/로드 (SaveSystem)
    - SaveSystem           : JSON 직렬화/역직렬화, persistentDataPath 저장
    - GameStateData        : 전체 게임상태 직렬화 구조체
    - CharacterUnitData    : 캐릭터 저장 데이터
    - StatManagerData      : 스탯 저장 데이터
    - StatData             : 개별 스탯 저장 데이터
    - GuildData            : 길드 저장 데이터

  [ + C 조합에 함께 필요한 의존 클래스 (자동 포함) ]
    - GameManager          : DayManager + SaveSystem의 허브, 반드시 포함
    - GameStateSO          : 게임 초기 설정값 ScriptableObject
    - FactoryCharacterUnit : 캐릭터 생성 팩토리
    - FactoryGameState     : 게임상태 생성 팩토리
    - CharacterDatabase    : 캐릭터 데이터 싱글턴
    - CharacterLevelDatabase : 레벨 진행 데이터
    - GameState            : 전체 게임 상태 컨테이너
    - Guild                : 길드 데이터 (GameState의 구성요소)

e. 다른 방법들 중에서 왜 d의 방식으로 만든 것인지
================================================================

  [ 진행 순서 선택 이유: C → B → A ]

  왜 C부터인가?
  ─────────────
  ✅ C 조합(Utils + 캐릭터 + Day + Save)은 게임의 "핵심 루프"다.
     - "캐릭터가 있고 → 하루가 지나며 → 저장된다"는 흐름이
       전략 게임의 가장 기본 뼈대
     - A 조합(파견/임무)도 결국 캐릭터와 Day 시스템 위에 얹힌다
     - B 조합(경로탐색/오디오)은 독립적이라 언제든 추가 가능

  왜 B가 2순위인가?
  ─────────────────
  ✅ B 조합(경로탐색 + 오디오)은 완전 독립 시스템이다.
     - PathFinder는 어떤 시스템에도 의존하지 않아 C 이후에도,
       심지어 A 이후에도 추가 가능
     - 오디오도 독립적이므로 씬 테스트 단계에서 추가하기 좋음
     - C 완료 후 씬 기본 동작 확인 시점에 함께 추가하면 효율적

  왜 A가 마지막인가?
  ──────────────────
  ✅ A 조합(파견/임무 + 길드)은 C가 완성된 후에야 의미를 갖는다.
     - MissionUnit은 DayManager, CharacterUnit 모두 필요로 함
     - 길드(Guild)는 이미 C 조합 복사 시 GameState와 함께 포함됨
     - 임무 시스템만 추가하면 A 조합 완성

  [ 다른 시작 순서와 비교 ]

  A부터 시작하는 경우:
  → 임무 시스템이 Day와 Character 모두 요구하므로
    결국 C의 내용을 먼저 복사해야 한다. 비효율적.

  B부터 시작하는 경우:
  → 동작은 하지만 게임 로직이 없어 "씬에 아무것도 없는" 상태.
    성취감과 검증 효과가 낮음.

  전체를 한 번에 하는 경우:
  → 컴파일 에러가 한꺼번에 터져 원인 추적이 어려움.
    Phase별 격리 없이는 디버깅이 매우 힘들어짐.

h. 주의할 점
================================================================

  ① FindObjectOfType → FindFirstObjectByType 수정 필수
  ─────────────────────────────────────────────────────
  Singleton.cs에서 FindObjectOfType를 사용 중이다.
  Unity 6에서는 deprecated이며 경고가 뜨고 향후 제거 예정.
  복사 즉시 수정할 것. 다른 스크립트에도 같은 패턴이 있으면 전부 수정.

  ② DayMissionManager 의존성 주석 처리 순서 지키기
  ──────────────────────────────────────────────────
  Phase 4에서 DayManager를 복사할 때 DayMissionManager 참조를
  반드시 주석 처리해야 컴파일이 된다.
  Phase 8 이전에 주석 해제하면 에러 발생.

  ③ ScriptableObject 인스턴스는 Unity에서 직접 생성
  ──────────────────────────────────────────────────
  SO 파일 자체를 GameDispatchLike에서 복사하면 GUID 충돌 위험.
  스크립트(.cs)만 복사하고, 인스턴스는 현재 프로젝트에서
  Create → 새로 생성하는 것이 안전하다.

  ④ TextMesh Pro 관련 폴더 절대 복사 금지
  ─────────────────────────────────────────
  GameDispatchLike의 TextMesh Pro 폴더를 복사하면
  현재 프로젝트의 TMP 설정과 충돌해 VisualNovel 씬 파괴 가능.

  ⑤ 각 Phase 후 반드시 컴파일 확인 후 다음 진행
  ────────────────────────────────────────────────
  에러가 남아있는 상태에서 다음 파일을 복사하면
  에러가 누적되어 원인 추적이 불가능해진다.
  각 Phase 완료 후 Unity Console 에러 0인지 확인 필수.

  ⑥ 컴파일 에러 상태에서 Unity 종료 금지
  ─────────────────────────────────────────
  씬 파일이 손상될 수 있다.
  에러 상태에서는 반드시 수정 후 종료.

  ⑦ 복사 전 git commit 필수
  ───────────────────────────
  각 Phase 시작 전 또는 Phase 완료 후 commit하여
  문제 발생 시 해당 Phase만 되돌릴 수 있도록 한다.
  권장 커밋 메시지 예시:
    "StrategyGame: Phase1 - Utils 복사 완료"
    "StrategyGame: Phase4 - Day 시스템 복사 (MissionMgr 주석처리)"

  ⑧ DOTween 설치 불필요 (C+B+A 범위)
  ────────────────────────────────────
  실제 스크립트 확인 결과, C#로직 레이어에서 DOTween 미사용.
  UI/View 시스템(⑨)을 추가할 때에만 DOTween이 필요하다.
  지금은 설치하지 않아도 된다.
